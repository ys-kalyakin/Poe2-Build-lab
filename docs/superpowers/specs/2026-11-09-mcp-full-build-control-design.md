# MCP: полное управление билдом внешним ИИ-агентом — дизайн

Дата: 2026-11-09
Статус: черновик на утверждение

## Замысел и почему

Poe2-Build-lab уже умеет управляться ИИ-агентом через MCP-сервер `PBLMcp`
(stdio, C# ModelContextProtocol SDK): есть headless-инструменты движка
(`PBLTools`), headless-драйвер MVVM (`AppTools`) и управление живым клиентом
через HTTP IPC (`VisualTools`, ~45 инструментов + ~80 эндпоинтов
`PBLApp/Ipc/IpcServer.cs`).

Но покрытие дырявое: агент **не может** собрать билд целиком —

- дерево: нет allocate-path / deallocate / списка занятых узлов / поиска узлов
  (IPC `/tree/toggle-node` существует, но в MCP не завёрнут);
- скилы: нет мутаций через IPC вообще (добавить/убрать группу, гемы, уровень,
  качество, вкл/выкл) — только headless-путь;
- нет чтения полных статов, сохранения билда, доступа к Config-табу в живом
  клиенте;
- часть готовых IPC-эндпоинтов не завёрнута в MCP-инструменты;
- `VisualLaunchClient` ищет только `PBLApp.exe` — на Linux-машине разработчика
  (где и работает агент) клиент не запустится.

Цель: агент (ZCode, Claude Desktop и т.п.), подключённый по MCP, может
**полноценно строить и управлять билдом в запущенном приложении** — экипировка
(уже есть), дерево, скилы, конфиг, статы, сохранение — и видеть результат
пользователем в реальном времени.

## Цели / не-цели / анти-цели

**Цели**
1. Дерево: агент строит путь от занятых узлов до цели, снимает узлы, читает
   занятое и ищет узлы по имени/статам.
2. Скилы: полный CRUD групп и гемов через IPC (группа, гемы, уровень,
   качество, вкл/выкл, include in Full DPS).
3. Статы: полные (~600) и фильтрованные из живого клиента.
4. Сохранение: сохранить билд в его XML; вернуть XML наружу.
5. Config-таб: читать секции/опции и выставлять значения (влияет на статы).
6. Заметки: агент пишет рекомендации в Notes-таб (пользователь видит).
7. Докрутить обёртки уже готовых IPC-эндпоинтов (tooltips скилов,
   support-picker, ui/text, импорт/экспорт).
8. Запуск клиента на Linux (`dotnet PBLApp.dll`) + на Windows (`.exe`).
9. Документация: как подключить ZCode/Claude Desktop, каталог инструментов,
   рецепты рабочих сценариев.

**Не-цели** (осознанно отложены)
- Чат с LLM внутри приложения (пользователь решил: пока не нужен).
- Рефакторинг «общего слоя инструментов» (реестр действий для IPC+MCP+чат) —
  шаг C из обсуждения; нынешний паттерн IPC→MCP сохраняется, чтобы рефакторинг
  потом был дешёвым.
- Undo/redo агентских действий (агент умеет откатывать явными действиями).
- Автосборщик билдов (решатель), автоматизация трейдера сверх существующего.

**Анти-цели** (что считаем провалом)
- Агент меняет билд, а пользователь этого не видит (значит, делаем через
  живой клиент, не headless).
- Инструменты, ломающие билд без диагностики (молчаливый partial-allocate).

## Ограничения

- Среда разработки — Linux (dotnet в `~/.dotnet`); VisualTools должен работать
  и на Windows, и на Linux.
- IPC-обработчики выполняются на UI-потоке через `OnUi`/`OnUiAsync` — новые
  эндпоинты следуют этому паттерну.
- Мутации — на уровне существующих ViewModel (`SkillsTabViewModel`,
  `TreeTabViewModel`), как это уже делают items-эндпоинты.
- Аллокация дерева обязана уважать бюджет очков и границы восхождений.

## Подходы (рассмотренные)

**A. Добить VisualTools + IPC (выбран).** Все новые возможности добавляются
эндпоинтами в `IpcServer` и MCP-обёртками в `VisualTools`, по сложившемуся
паттерну. Агент работает с живым приложением, которое видит пользователь.
Торговля: VisualTools растёт (~+25 инструментов, суммарно ~100) — приемлемо
для MCP-клиентов.

**B. Headless-путь (RunLua / PBLTools).** Быстро, но пользователь не видит
результат, и часть стека (трейдер, татуировки, heatmap) headless не покрывает.
Отклонено как основной путь; headless остаётся для тестов/CI как есть.

**C. Общий слой инструментов сразу.** Реестр действий в PBLApp, который едят
IPC, MCP и будущий чат. Правильная конечная точка, но самый большой первый
шаг, а чат отложен. Отклонено на сейчас; паттерн A этому не мешает.

## Решения (как строим)

### 1. Новые IPC-эндпоинты (PBLApp/Ipc/IpcServer.cs)

| Эндпоинт | Тело | Ответ |
|---|---|---|
| `/tree/allocated` | — | `{ids:[...], nodes:[{id,name,type,ascendancy}], points, budget, overBudget}` |
| `/tree/allocate-path` | `{nodeId, attribute?}` | `{ok, path:[ids], allocated:[ids], pointsSpent, pointsLeft, budget, overBudget, attributeNodes:[{id, picked}]}` или ошибка (недостижим) |
| `/tree/deallocate-node` | `{nodeId}` | `{ok, freed:[ids]}` или `{error, dependents:[ids]}` |
| `/tree/nodes` | `{query?, nearId?, limit?=50}` | `{nodes:[{id,x,y,name,stats,linkedIds,allocated,ascendancy}]}` |
| `/skills/list` | — | `{groups:[{index,name,isMain,enabled,includeInFullDps,gems:[{name,level,quality,enabled,isSupport}]}]}` |
| `/skills/add-group` | `{gemName}` | `{ok, index}` |
| `/skills/remove-group` | `{index}` | `{ok}` |
| `/skills/add-gem` | `{group, gemName}` | `{ok, gemIndex}` |
| `/skills/remove-gem` | `{group, gem}` | `{ok}` |
| `/skills/set-gem` | `{group, gem, name?, level?, quality?, enabled?}` | `{ok}` |
| `/skills/set-group` | `{group, enabled?, includeInFullDps?, label?}` | `{ok}` |
| `/skills/set-main` | `{group}` | `{ok}` (активная группа — от неё считается Full DPS) |
| `/stats` | `{keys?}` | объект статов (как headless `app_get_stats`) |
| `/build/save` | — | `{ok, path}` |
| `/build/xml` | — | `{xml}` |
| `/notes` | GET / `{text}` | `{text}` / `{ok}` |
| `/config/state` | — | `{sections:[{name,options:[{var,label,type,value,listOptions}]}]}` |
| `/config/set` | `{var, value}` | `{ok}` |

Обёртки существующих: `/skills/tooltips`, `/skills/support-picker*`,
`/tree/set-search`, `/tree/toggle-node`, `/tree/node-text`, `/ui/text`,
`/character-import/open`, `/export/open`, `/build/update-from-game`.

Таблица — не исчерпывающий контракт: при обёртке разрешено добавлять мелкие
мутации, которые уже поддерживает движок/VM (как `/skills/set-main` выше);
итоговый каталог фиксируется в `docs/mcp.md`. Опциональные просмотр-эндпоинты
(`/app/screens`, `/tree/hover-node`) не обёртываются — агенту не нужны.

### Решения по семантике (мои, проверьте при чтении)

1. **Бюджет очков**: allocate-path выделяет весь путь, как это делает UI
   (перебор разрешён, счётчик краснеет), но ответ всегда честен:
   `pointsSpent`, `pointsLeft`, `overBudget` — агент сам решит откатить.
   Никаких молчаливых частичных аллокаций.
2. **Синхронная правда движка**: мутационные эндпоинты дерева возвращают ответ
   только после того, как Lua-движок применил изменение и VM сверилась с ним
   (новый публичный API ожидания дрена `_luaQueue` + reconcile в
   `TreeTabViewModel`). Латентность ~130 мс/узел в худшем случае — приемлемо
   для агента; зато `/stats` сразу после мутации не врёт.
3. **Атрибутивные узлы** («+5 к любому атрибуту») на пути: берутся
   автоматически с дефолтом движка; ответ перечисляет их с выбранным
   атрибутом (`attributeNodes`); опциональный параметр `attribute` позволяет
   указать желаемый (для одиночного узла).
4. **Заметки**: POST `/notes` пишет и в VM, и в `_build.Notes` (тогда
   `/build/save` их сохраняет). Окно заметок само не открываем — агент и так
   пересказывает рекомендации в своём ответе.
5. **Адресация в `/skills/*`**: индексы движка, 1-based, как в
   `/skills/tooltips`; каждый мутационный ответ возвращает освежённый
   `/skills/list`-срез, чтобы агент переадресовывался после удалений
   (индексы сдвигаются). Пустые VM-слоты (`GemIndex == 0`) в контракт не
   входят — новый гем добавляется только `/skills/add-gem`.

### 2. Изменения в ViewModel (PBLApp.Core)

- `TreeTabViewModel`:
  - публичный `AllocatePathTo(int nodeId)` — BFS кратчайшего пути по
    `LinkedIds` от занятой границы к цели; BFS-логика выносится в статический
    чистый метод `TreePathFinder.FindPath(allocSet, nodes, targetId)` для
    юнит-тестов; аллокация — через существующие внутренние методы
    (по одному узлу пути, с `OnStatsChanged` как у `ToggleNodeTimed`);
    недостижимость (чужое восхождение без входа в него) — явная ошибка;
  - публичный `DeallocateNode(int nodeId)` — рефанд только «листа» (узла, на
    который никто не опирается); иначе ошибка со списком зависимых;
  - публичный API ожидания дрена очереди Lua + reconcile (см. решение 2
    ниже) — на нём держится «синхронная правда» мутаций;
  - `Nodes` уже `IReadOnlyList<TreeNodeDto>` (Id, X, Y, Name, Stats,
    LinkedIds, AscendancyName) — `/tree/nodes` ищет по нему без изменений VM.
- `BuildPageViewModel`: публичный `Task SaveNow()` (обёртка над приватным
  `SaveBuildAsync`) — используется `/build/save`.
- `ConfigOptionViewModel`: выставление значения по `Type`
  (checkbox → bool, list → `ConfigListItem` по совпадению, text →
  `ApplyText`); при необходимости добавить публичный сеттер-метод.
- `NotesTabViewModel`: уже держит текст — добавить публичный доступ для IPC.

### 3. MCP-инструменты (PBLMcp/VisualTools.cs)

Имена `visual_tree_*`, `visual_skills_*`, `visual_get_stats`,
`visual_build_save`, `visual_build_xml`, `visual_notes`, `visual_config_*`,
`visual_ui_text`, `visual_character_import`, `visual_export_open`,
`visual_update_from_game`. Каждый — тонкая обёртка над одним эндпоинтом,
описания самодостаточные для агента (что возвращает, что требует).

### 4. Кроссплатформенный запуск клиента

`VisualTools.VisualLaunchClient`: искать `PBLApp.exe` (Windows) либо
`PBLApp.dll` + запуск через `dotnet` (Linux/macOS). Аналогично в документации
указать путь публикации.

### 5. Документация

- `docs/mcp.md` — что такое PBLMcp; конфиг подключения для ZCode (`.zcode`
  settings, `mcpServers`) и Claude Desktop (`claude_desktop_config.json`);
  запуск `dotnet run --project PBLMcp`; различие headless- и `visual_*`
  инструментов; рецепты: «проанализируй билд», «сравни два предмета»,
  «перебери путь на дереве», «собери скил-сетап», «сохрани билд»; каталог
  инструментов таблицей.
- README: короткая секция со ссылкой на `docs/mcp.md`.
- `CHANGELOG.md`: запись о новом MCP-покрытии.

### 6. Тесты

Дом тестов — `PBLEngine.Tests` (уже ссылается на PBLApp.Core; паттерны —
существующие `SkillsTabTests.cs`, `TreeTabTests.cs`):

- Юнит: `TreePathFinder` — кратчайший путь, старт от ближайшего занятого,
  отказ при недостижимом узле (другое восхождение), отказ deallocate узла с
  зависимыми.
- VM-уровень: CRUD скилов на реальных `SkillsTabViewModel`, `/stats`-эквивалент
  через `BuildModel.AllStats`, `SaveNow` в=temp-файл.
- IPC-эндпоинты — тонкие, тестируются e2e-проходом агентом (руководство в
  `docs/mcp.md`).

## Что остаётся строителю

- Точная сигнатура BFS-поиска и его место в файле.
- Разметка `/tree/nodes` (регистронезависимый substring по Name и Stats;
  `nearId` — сортировка по дистанции на карте).
- Как именно `ConfigOptionViewModel` применяется для каждого `Type` —
  по фактическому коду (там уже есть `ApplyText`).
- Тексты описаний MCP-инструментов (содержательные, но короче 2 строк).
- Порядок коммитов (логично: IPC-эндпоинты → VM-методы → MCP-обёртки →
  доки/тесты).
